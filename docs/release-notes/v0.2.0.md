# Open Health Sync v0.2.0

The release for running an instance, not only reading from it. The admin console now runs the
pipeline, an admin API serves instances shared by several teams, and each tenant can bring its
own provider keys. Five new ways in: Garmin, Eight Sleep, Xiaomi, activity files (FIT, GPX, TCX)
and standard Bluetooth health devices through the new `ohs-bridge`. ECG recordings are served,
and self reports, share links, sample statistics, encryption key rotation and signed releases are
new. Still an early preview: APIs, configuration and schema may change in any 0.x release, so pin
the version you run.

## Install

Container image (`linux/amd64`, `linux/arm64`):

```sh
docker pull ghcr.io/soma-intelligence/open-health-sync:0.2.0
```

The image is tagged `0.2.0` and `edge`. There is no `latest` tag while the version is 0.x.
Binaries for Linux and macOS on amd64 and arm64 and the Android example app
(`ohs-example-android.apk`) are attached below, with `checksums.txt` (SHA-256).

This is the first release signed with Sigstore cosign, keyless, by the release workflow's GitHub
identity: the image by its digest, and `checksums.txt` with the bundle
`checksums.txt.sigstore.json`. The commands to check both are in
[SECURITY.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/SECURITY.md#verifying-releases).

The [quickstart](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/README.md#quickstart)
runs it with Docker Compose, [Render, Fly.io or Railway](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/deploy-platforms.md)
host it for you, and the [Helm chart](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/helm.md)
(chart 0.2.0) runs it on Kubernetes.

## What's new

### Running an instance

- **The console runs the pipeline.** `/console` shows the five stages (sources, sync,
  processing, storage, delivery) with what needs attention, and acts on them: turn providers on
  and save their keys, create users and send them a connection link, start a sync, retry parked
  processing jobs, manage webhook endpoints and deliveries, create and revoke API keys, read the
  audit log. Every action calls a documented route with the tenant key and asks for a
  confirmation first. [docs/console.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/console.md)
- **Providers turned on without a restart.** An instance admin saves a provider's keys with
  `PATCH /v1/admin/providers/{provider}`. Keys are checked by the connector, sealed with
  `OHS_ENCRYPTION_KEY`, never returned, and picked up by every process within 30 seconds.
  `OHS_<PROVIDER>_*` variables still win when set.
- **Admin API for several teams.** With an instance admin key, `/v1/admin/tenants` creates and
  lists tenants and manages their keys, turns a provider on or off for one tenant, fills a demo
  user, and serves a tenant's whole API (users, data, connections, webhooks, jobs, audit log)
  under `/v1/admin/tenants/{tenant_id}`, so a portal can run a team's projects with no tenant key
  in a browser. Every change is audited on both tenants.
  [docs/admin-api.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/admin-api.md)
- **A tenant's own provider keys.** `PUT /v1/admin/tenants/{tenant_id}/providers/{provider}/keys`
  sets a tenant's own OAuth application, so its users see its name on the consent screen. Each
  connection keeps the keys it was made with; replacing the client id sets those connections
  `needs_reauth` with a `connection.needs_reauth` webhook.
- **Tenants manage their own keys** with `GET`, `POST /v1/keys` and `DELETE /v1/keys/{key_id}`,
  and read their pipeline with `GET /v1/pipeline`, `.../sync-runs` and `.../etl-jobs` (with
  retries).
- **First-run setup in the browser** for app store installs with no terminal (Umbrel, CasaOS):
  `OHS_SETUP_TOKEN` and `/console/setup` create the first tenant once. With
  `OHS_ENCRYPTION_KEY_FILE` and `OHS_SETUP_TOKEN_FILE`, a missing file is filled with a random
  value on first start, so every install gets its own key.
  [docs/setup.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/setup.md)
- **Encryption key rotation online.** Put the new key in `OHS_ENCRYPTION_KEY`, the old one in
  `OHS_PREVIOUS_ENCRYPTION_KEYS`, run `ohs admin rekey`; `ohs doctor` says when the old key can
  go. [docs/key-rotation.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/key-rotation.md)
- **Rate limits** on the provider-facing routes (`/inbound/{provider}`, the OAuth callback): 429
  with `Retry-After` before any work. `OHS_TRUSTED_PROXIES` names the proxies whose
  `X-Forwarded-For` is read.

### New sources

- **Garmin** (Health API, OAuth 2.0 with PKCE): dailies, epochs, sleep stages, activities, body
  composition, HRV, pulse ox, respiration, VO2 max, blood pressure, skin temperature, with
  Garmin's ping and push notifications. Garmin gives keys to approved businesses only, and every
  instance brings its own.
- **Eight Sleep**: nightly sleep stages and score, heart rate, HRV, respiratory rate, bed and room
  temperature, through the sign-in the Eight Sleep app uses (no public API). A new sign-in page
  serves providers that take a password instead of OAuth; the password is sealed and never logged.
- **Xiaomi**: `ohs import mi-fitness` loads the data copy Xiaomi sends from its privacy center.
  Health Connect records of Mi Fitness, Zepp (Amazfit) and RingConn get their own source slugs.
- **Activity files**: `ohs import files` loads FIT, GPX and TCX files and whole account exports
  (Garmin, Strava, COROS, Wahoo, Zwift, Suunto, Polar), with GPS routes, per-second heart rate
  and power. Each file is sent once.
- **Bluetooth devices**: heart rate straps, blood pressure cuffs, scales, glucose meters,
  thermometers and pulse oximeters that use the standard Bluetooth health profiles send their
  readings straight to `POST /v1/ingest/bluetooth`, with no vendor account. `ohs-bridge`, a Rust
  desktop bridge for macOS, Linux (Raspberry Pi included) and Windows, scans, reconnects, spools to
  disk and uploads; it also uploads new FIT files from a mounted watch. The Swift and Kotlin SDKs
  can record and upload the same parts.
  [docs/bridge.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/bridge.md)
- **Health Connect nutrition and energy**: nutrition, hydration, total energy burned and basal
  metabolic rate.

### New data and outputs

- **ECG recordings are served**: `GET /v1/users/{id}/ecg` and `.../ecg/{ecg_id}` with voltage
  samples, in FHIR (LOINC 11524-6 with `valueSampledData`), MCP and exports. The classification is
  the device's own; nothing is computed from the signal.
- **Self reports**: `POST /v1/users/{id}/self-reports` stores a person's own ratings (how they
  feel, mood, stress, energy, sleep quality, soreness, effort, pain) as samples of the new
  `self_report` source. [docs/self-reports.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/self-reports.md)
- **Share links** (SMART Health Links): a person shares a time window of some categories with
  whoever they choose, encrypted, with an expiry, an optional passcode and a built-in viewer.
  Every access is audited. [docs/share-links.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/share-links.md)
- **Sample statistics**: `GET /v1/users/{id}/samples/stats` and the MCP tool `get_sample_stats`
  give count, sum, mean, min and max per hour or local day in any time zone. A year of daily heart
  rate takes 31 ms instead of 443 ms.
- **Intensity minutes** (`moderate_activity_time`, `vigorous_activity_time`) from Oura and
  Withings, and FHIR measures that follow the HL7 Physical Activity IG.
- **Nutrition logs in FHIR**, as Observations with LOINC coded components.
- **`data_types` on `GET /v1/providers`**: which record kinds and quantities each source gives.
- **MCP prompts**: twelve ready-made questions about training, sleep and recovery, also published
  as an agent skill.
- **Demo personas**: `ohs seed --demo --persona runner|sleep|weight`.
- **A web example** (Next.js, TypeScript server SDK) from the first user to webhooks.

### Faster

- Merged view reads on a long history: a FHIR page of 1,000 over a recent week went from 5.5 s to
  0.35 s, and `/samples` of 1,000 heart rates from 1.2 s to 0.17 to 0.5 s.
- FHIR Observation pages read only the chunks they lie in: the full export of 125,200
  Observations went from 47 s to 24 s.

### Fixed

- Apple Health energy in `Cal` (kilocalories) was stored 1,000 times too low, and food entries in
  kilograms landed 1,000 times too low in `protein_g`. Every nutrient now has one documented unit,
  and a unit that does not convert rejects the record.
- Apple Health nights are whole again: a night across midnight, a night "in bed" with no figures
  and a nap uploaded with a night are each one session with all their stages.
- `GET /v1/users/{id}/connections` returns the fields `api/openapi.yaml` documents, which the
  Swift and Kotlin SDKs need to decode the list.
- Disconnecting a user revokes the Oura token, and provider deletion notices keep `push_healthy`
  true.
- MCP `get_coverage` without `start` reports the last 30 days instead of over a megabyte.
- Suunto: one workout with a field of an unexpected type no longer drops its whole page.

The full list is in the [changelog](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/CHANGELOG.md#020---2026-10-21).

## Upgrade notes

Take a backup first, then set `OHS_VERSION=0.2.0` in your `.env`, pull and recreate (the
[self-hosting guide](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/self-hosting.md#upgrading)
has the full steps). CI upgrades a v0.1.0 database to this release and checks that its data is
still served. A v0.1.0 configuration starts as is, with these changes in behavior:

- **`OHS_CONSOLE=true` now serves the console with its actions.** An instance that turned it on
  for the read-only view gets them on upgrade. Set `OHS_CONSOLE=read-only` to keep the console
  without any action.
- **A single-tenant instance's tenant becomes its instance admin** (migration `0038`), so the
  console can turn providers on. An instance with several tenants gets no admin until you name
  one with `ohs admin tenant admin --tenant <id>`. Only admin keys reach `/v1/admin/*`.
- **The FHIR Observation search answers 400 for a parameter it does not support.** `date` and
  `_count` used to be ignored and returned the whole list. Use `start`/`end` and `limit`.
- **ECG atrial fibrillation classifications (Withings) are a `valueCodeableConcept`** in FHIR
  (`negative`, `positive`, `inconclusive`) instead of a quantity in the unit "classification".
- **Eight Sleep is on by default**, since it needs no keys. Turn it off in the console if you do
  not want your users to see it.
- **A nutrient in a unit that does not convert now rejects its record** instead of storing it in
  the wrong unit.
- **Values stored wrong before stay wrong until re-imported.** For Apple Health energy in `Cal`
  and nutrients in kilograms, erase the provider's data
  (`DELETE /v1/users/{id}/data/apple_health`) and import the export again. To rebuild nights
  split by 0.1.0, see [the Apple Health guide](https://github.com/soma-intelligence/open-health-sync/blob/v0.2.0/docs/connectors/apple-health.md#sleep).
- **The recipes are Go programs** (`go run ./recipes/<name>`), with the same flags and output.

Migrations `0035` to `0042` apply on start. `0035` creates the `quantity_hourly` continuous
aggregate empty, so the migration is quick; its policy then fills the whole history in the
background, every 5 minutes, and `samples/stats` reads the raw samples for hours not filled yet.
On a large database, expect the first runs to load the server. Builds without continuous
aggregates (an Apache-only TimescaleDB) skip it and read the samples.

## Known limitations

- Fitbit needs a Google Health API project, and Google is not onboarding new ones yet. Garmin
  keys go to approved businesses only. Most other cloud sources need a developer or partner app
  of your own with the provider; each connector guide says which.
- Eight Sleep uses the sign-in of the Eight Sleep app, not a public API, so it can break when the
  app changes.
- FHIR R4 has no bulk export (`$export`) yet.
- After a hard kill, a job that was in flight is picked up again only after its 10 minute
  visibility timeout. One database and one raw store per instance.
