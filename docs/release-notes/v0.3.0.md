# Open Health Sync v0.3.0

Health data is now sealed per user at rest, API keys take scopes, events stream over
Server-Sent Events, lab results can be uploaded, and every mobile SDK reads the phone's health
store. Each provider is also pulled on its own schedule, deleted and edited HealthKit samples
leave the server, and a stress and fuzz pass fixed how `ohs` behaves under load, during database
outages and on bad input. Still an early preview: APIs, configuration and schema may change in
any 0.x release, so pin the version you run. Read [Upgrading](#upgrading) before you do: this
release changes behaviour in several places.

## Install

Container image (`linux/amd64`, `linux/arm64`):

```sh
docker pull ghcr.io/soma-intelligence/open-health-sync:0.3.0
```

The image is tagged `0.3.0` and `edge`. There is no `latest` tag while the version is 0.x.
Binaries for Linux and macOS on amd64 and arm64 and the Android example app
(`ohs-example-android.apk`) are attached below, with `checksums.txt` (SHA-256). The image and
`checksums.txt` are signed with Sigstore cosign, keyless; the commands to check both are in
[SECURITY.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/SECURITY.md#verifying-releases).

The [quickstart](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/README.md#quickstart)
runs it with Docker Compose, [Render, Fly.io or Railway](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/deploy-platforms.md)
host it for you, and the [Helm chart](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/helm.md)
(chart 0.3.0) runs it on Kubernetes.

## Highlights

- **Health data vault.** Every health value at rest is sealed under keys of one user: the values,
  metadata, source and device fields of each row in one XChaCha20-Poly1305 seal, raw payloads
  sealed at ingestion to the user's public keys (ML-KEM-1024 and X25519), dedup hashes keyed per
  user. Ids, record types, times, units and providers stay clear for queries. Erasing a user
  shreds their keys first. The root key is local (by default derived from `OHS_ENCRYPTION_KEY`,
  or `OHS_VAULT_ROOT_KEY`), in HashiCorp Vault transit, Azure Key Vault or AWS KMS. New
  commands: `ohs vault status`, `seal`, `rotate root|tenant|user` and `reseal`.
  [Security model](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/security-model.md#health-data-vault)
- **API key scopes.** A key holds `*` or a list of 18 scopes (`users:read`, `data:write`,
  `webhooks:write`, ...); every route needs exactly one, and a user token never does more than
  the key that minted it. [Key scopes](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/api.md#key-scopes)
- **Event stream.** `GET /v1/events/stream` and `GET /v1/users/{id}/events/stream` send the
  events webhooks carry as Server-Sent Events, resumable for 24 hours with `Last-Event-ID`, for a
  backend with no public HTTPS receiver. The server SDKs gain `streamEvents` and
  `stream_events`. [Event stream](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/events-stream.md)
- **Lab results.** `POST /v1/users/{id}/labs` takes FHIR R4 (Bundle, DiagnosticReport,
  laboratory Observation) or a JSON form; results keep LOINC codes, ranges, flags and status, an
  amended copy replaces the earlier one, and they are read back over REST, as FHIR Observations
  and DiagnosticReports, in exports and through MCP, with a `labs` consent category.
  [Lab results](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/labs.md)
- **Every mobile SDK reads the health store.** The Kotlin SDK's `open-health-sync-health-connect`
  module reads Health Connect (incremental, offline queue, background job); the React Native
  native module and the Flutter plugin read HealthKit and Health Connect through the Swift and
  Kotlin SDKs. The Swift SDK adds workout routes, ECG, heartbeat series, audiograms and states
  of mind, client methods for connect sessions, stats, RR intervals, HRV, ECG, time tags and
  self reports, and installs by repository URL. [SDKs](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/sdks/README.md)
- **Wahoo and a sandbox provider.** Wahoo workouts, body mass and height over OAuth with
  webhooks. The sandbox provider (`OHS_SANDBOX_ENABLED=true`) runs a whole OAuth connect flow
  inside the instance with synthetic data, to evaluate without a vendor account. Pages for
  Peloton, Zwift, MyFitnessPal and Cronometer say why there is no connector and how their data
  comes in. [Connectors](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/connectors/README.md)
- **ECG, routes and heartbeat series as one blob per series**, compressed then sealed: 9.2 bytes
  a point for an ECG (was 653 sealed), 30.7 for a route (696), 3.7 for a heartbeat (630). The API
  serves the same output.
- **Worker health.** A process without the `api` role serves `/healthz`, `/readyz` and
  `/metrics` on an ops listener; `/healthz` names a background loop that stopped. Queue depth,
  oldest job age and job duration metrics. [Observability](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/observability.md#health)
- **A time zone per user**, set with `PATCH /v1/users/{id}` or learnt from device uploads; a
  sample with no zone of its own counts toward the user's local day.
- **Bounded ETL memory.** A 64 MiB Apple Health part peaked at 536 MiB of heap sealed; it now
  peaks near 42 MiB.

## Also in this release

### Sync

- **A sync policy per provider.** Each connector declares how often it is pulled with and
  without notifications, how far each pull reads again for late or revised data, how far a new
  connection is backfilled, and an optional daily reconciliation. Dexcom re-reads 6 hours (its
  readings reach the API up to 3 hours late outside the US), OMRON 72 hours, Ultrahuman 48;
  Oura, WHOOP, Withings and Dexcom are backfilled over 90 days, Polar and Suunto over the 28 days
  their APIs keep. The table is in
  [background sync](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/background-sync.md#sync-policy-per-provider).
- **The console shows each provider's schedule.** A provider's page lists how often it is
  pulled, how far each pull reads again and how far a new connection is backfilled, and
  `GET /v1/admin/providers` serves the same as `sync`.
- **A failed pull window is fetched again.** The regular pull reaches back to the end of the last
  complete pull instead of the last successful job.

### Apple Health

- **Deleted and edited HealthKit samples are removed from the server.** HealthKit edits a sample
  by deleting it and saving a new one, so every edited weight or blood pressure used to stay
  twice. The Swift SDK now uploads deletion lines, and a sample is removed only once no other
  copy stands for it (migration `0043`).
  [Deletions](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/connectors/apple-health.md#deletions)
- **US units in export.xml**: heights in feet, masses in ounces, lengths in inches, speeds in ft/s
  and volumes in fluid ounces are converted instead of refused.

### Running under load and outages

- **Memory**: the compose file caps `ohs` at 1 GB and `ohs` sets `GOMEMLIMIT` to three quarters of
  the container limit. [Memory profiles](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/self-hosting.md#memory),
  the Raspberry Pi one included.
- **Uploads**: one tenant can no longer hold every ingest slot, and an uploaded part may expand to
  64 MiB once decompressed (`OHS_INGEST_MAX_DECOMPRESSED_MIB`, up to 512).
- **Outages answer 503 with `Retry-After`**, not 500: a database restarting, out of connections or
  not answering, and a full or read-only raw store. A frozen database no longer holds requests
  for minutes, and jobs in flight during a Postgres restart are retried after their usual
  backoff instead of a 10 minute wait.
- **Slow clients**: a request must be read within 2 minutes (uploads keep 5), and
  `OHS_MAX_CONNECTIONS` (default 4096) caps open connections.

### Data quality

- Sleep phases, ECG recordings, daily summaries, observations and workout figures are now
  range-checked, and every record kind refuses a time before 1990. One bad figure no longer
  costs the whole record: it is dropped and listed under `quality_dropped` in the record's
  metadata.
- NaN and infinite values, NUL characters and invalid UTF-8 are refused or cleaned instead of
  stored or answered with a 500.
- New connector fuzz tests found and fixed overflowing durations, zero times and unit conversions
  in a dozen connectors.

### Limits, keys and tokens

- Authenticated routes are rate limited per credential, refused credentials are recorded as
  `auth.failed` and throttled per address, and every authenticated response carries
  `Cache-Control: no-store`.
- User tokens can be revoked, one or all of a user, and revoking an API key revokes the tokens it
  minted. API keys can carry an expiry.
- Failed sync runs can be retried, one or all of a connection. Provider outages are retried for
  about three days before a pull gives up.
- One large import no longer delays other users, one provider's backlog no longer delays other
  providers, and one slow webhook endpoint no longer delays the others.
- A replayed job for an older raw object no longer overwrites a provider's newer revision.
- The S3 raw store can ask for server-side encryption.

### Also new

- `deploy/Caddyfile`: Caddy with automatic TLS in front of the compose stack.
- A synthetic data generator for every documented provider, run nightly through a live server.
- `internal/quality`: a first data quality score library with its backtest report. No API uses it
  yet. [docs/quality.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/quality.md)

The full list is in the [changelog](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/CHANGELOG.md#030---2026-11-11).

## Upgrading

Take a backup first ([`scripts/backup.sh`](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/backup-and-restore.md)), then set
`OHS_VERSION=0.3.0` in your `.env`, pull and recreate (the
[self-hosting guide](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/self-hosting.md#upgrading) has the full steps). Migrations `0043` to
`0055` apply on start. A v0.2.0 configuration needs one change, the database password of the
first point, and then starts with the changes below.

### Before and during the upgrade

- **The compose file requires `POSTGRES_PASSWORD`.** It no longer falls back to `ohs`. If your
  `.env` has no `POSTGRES_PASSWORD` line, add `POSTGRES_PASSWORD=ohs` to keep the password your
  database was created with, then rotate it as the
  [self-hosting guide](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/self-hosting.md#rotating-secrets) describes.
- **Migration `0050` rewrites `quantity_samples` once**, in one transaction, decompressing its
  compressed chunks batch by batch. It takes as long as a full rewrite of the table and needs the
  free disk space of the uncompressed table: on a large instance, plan a maintenance window. The
  compression policy recompresses within a day.
- **`ohs serve` refuses a database at another schema version.** Run `ohs migrate up` first (the
  compose file and the Helm chart do). `/readyz` answers not ready while the database is behind
  the binary. If a migration is stopped half way, `ohs migrate force <version> --yes` clears the
  mark.
- **No way back to 0.2.0 once a row is sealed.** New writes are sealed from the first start;
  0.2.0 cannot read them. To go back, restore the backup taken before the upgrade.

### The vault

- **Run `ohs vault seal` once after the upgrade**, then `ohs vault status --check`. The first
  start gives every tenant and user keys and seals new writes; rows, raw objects and per-point
  ECG, route and heartbeat rows stored by 0.2.0 stay in clear, and readable, until the seal
  converts them. It works in batches and can be stopped and run again.
- **The root key is derived from `OHS_ENCRYPTION_KEY` by default.** With no `OHS_VAULT_ROOT_KEY`
  and the `local` provider, losing `OHS_ENCRYPTION_KEY` now loses the health data as well as the
  OAuth tokens, and whoever holds it and a copy of the database reads both. Set a separate
  `OHS_VAULT_ROOT_KEY_FILE` (or `OHS_VAULT_ROOT_KEY`, 32 random bytes) or a KMS provider, run
  `ohs vault rotate root`, and back the root key up apart from the database. `ohs doctor` warns
  while the key is derived.
- **After `ohs vault rotate root`, restart every process.** A running one keeps the old root key
  and fails once its key cache expires (10 minutes by default).
- **After rotating `OHS_ENCRYPTION_KEY`, wait for `ohs admin rekey`** before removing the old
  key: with a derived root key it also rewraps the tenant keys under the new one.
- **Azure Key Vault and AWS KMS** need a binary built with `-tags azurekv,awskms`: the release
  binaries and image are; `make build` is not.

### Behaviour changes

- **API keys**: every existing key keeps full access (`*`). A route outside a scoped key's scopes
  answers 403 naming the scope.
- **Authenticated routes are rate limited**: 200 requests a second per credential, burst 2,000,
  answered with `429` and `Retry-After`. `OHS_RATE_LIMIT_API` changes it or turns it off. Refused
  credentials are throttled per client address: behind a reverse proxy, set `OHS_TRUSTED_PROXIES`
  so that address is the client's and not the proxy's.
- **Webhooks**: at most 2 requests in flight per endpoint and 4 per tenant (half of
  `OHS_WEBHOOK_CONCURRENCY`; an instance with one tenant that wants the former 8 sets
  `OHS_WEBHOOK_PER_TENANT=8`), an endpoint is paused after 5 consecutive failures, and after
  `rotate-secret` the previous secret also signs for 24 hours, so a receiver sees two signatures
  in the header during that time.
- **The event stream adds one row per event** (`ohs_core.stream_events`, kept 24 hours), written
  with the change it announces. `OHS_STREAM_MAX=0` turns the stream off and keeps no event.
- **Workers get an ops listener.** A process without the `api` role listens on `127.0.0.1:8081`
  (`OHS_OPS_LISTEN`, `off` to turn it off). Two workers on one host need an address each. The
  Helm chart probes the `collect` and `etl` pods of `splitRoles` with `httpGet` on that port
  (`splitRoles.opsPort`) instead of the `ohs doctor --quick` exec probe.
- **ECG voltages, workout routes and heartbeat series move into `ohs_data.series_blobs`**
  (migration `0053`) as each series is written again or sealed. A route point's `id` is now its
  position in the route (from 1), and an `/rr-intervals` cursor taken before the upgrade answers
  400 (beats that share a time are now ordered by provider, series and interval): start that
  listing again. `ohs migrate down` past `0053` refuses while a blob is stored.
- **Samples with no zone of their own** count toward the user's time zone when the user has one
  (set or learnt), instead of UTC. Days already derived keep the zone they were written in.
- **The ETL runs one job per user at a time** (`OHS_ETL_JOBS_PER_USER`).
- **`sync_log` rows and finished ETL jobs are pruned after 90 days**
  (`OHS_TRACKING_RETENTION_DAYS`).
- **The compose file caps `ohs` at 1 GB.** Raise `OHS_MEM_LIMIT` if your instance needs more.
- **Garmin notifications are refused while `OHS_GARMIN_INBOUND_TOKEN` is unset.** Set it and add
  `?token=<value>` to the notification URLs in Garmin's portal, or only the scheduled pulls bring
  data.
- **An uploaded part may expand to 64 MiB** instead of 512. The SDKs and `ohs import` send parts of
  at most 8 MiB, so they are not affected.
- **Outages answer 503** where they answered 500. Clients that retry 503 keep their uploads.
- **Values that used to pass and are now refused**: an oxygen saturation under 50 %, a body fat
  percentage under 2 % or over 80 %, negative nutrition figures, times before 1990.
- **Rows stored earlier keep their values.** To make Apple Health rows stored by 0.2.0 deletable,
  upload the history again (`resetAnchor` in the Swift SDK). Fitbit points relayed from Apple
  Health keep their old type and source until you run
  [the relayed points script](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/docs/how-to/fitbit-relayed-points.md).

## Known limitations

- **Vault.** It hides values, not the shape of the data: who has data of which type, from which
  provider and when stays readable. It is not zero knowledge: a process that holds the root key
  reads everything, and in the default deployment one process runs every role. A backup taken
  before an erasure still holds that user's data for whoever has the root key, until it expires
  or the root key is rotated and its previous version destroyed. The release that drops the
  clear columns is not built yet. HashiCorp Vault, Azure Key Vault and AWS KMS are tested
  against fakes of their APIs only.
- **Event stream.** Best effort, at most once per connection: an event can be missed when a
  connection drops, and events are kept 24 hours (10,000 at most to replay). The caps
  (`OHS_STREAM_MAX`, `OHS_STREAM_MAX_PER_TENANT`) are per `api` process. Use webhooks where every
  event must arrive.
- **Lab results.** Not served as Open mHealth and not in share links. Only laboratory results
  are taken (other FHIR categories are refused), only the first reference range and
  interpretation are kept, Observations with `component` are refused, and units are normalized
  only where the conversion is exact (not triglycerides). A result a later report no longer
  lists stays stored. Limits: 100 reports, 2,000 results and 1 MiB per upload.
- **Series blobs.** A series is stored and removed whole: retention drops a series only once its
  last point is past the cutoff. Apple Health deletions do not cover sleep stages, ECG and
  heartbeat series yet.
- **Health Connect zones.** Health Connect records carry an offset, not a zone name, so a user
  zone learnt from them is a fixed offset that does not follow daylight saving time. Set the
  user's zone with `PATCH /v1/users/{id}`.
- **Mobile readers.** The Kotlin Health Connect reader and the Flutter plugin have run in unit
  tests and builds only, on no device or emulator. The React Native module ran on an iOS
  simulator (it loads and stores its credentials; no real sync). No SDK is on a package registry
  yet.
- Fitbit needs a Google Health API project, and Google is not onboarding new ones yet. Garmin
  keys go to approved businesses only. Most other cloud sources need a developer or partner app
  of your own with the provider; each connector guide says which.
- Eight Sleep uses the sign-in of the Eight Sleep app, not a public API, so it can break when the
  app changes.
- FHIR R4 has no bulk export (`$export`) yet.
- The rate limits are kept per process.

## Security

Report vulnerabilities privately through
[GitHub Private Vulnerability Reporting](https://github.com/soma-intelligence/open-health-sync/security/advisories/new).
See [SECURITY.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.3.0/SECURITY.md).
This release refuses more reserved addresses as webhook destinations (NAT64, 6to4 and the
reserved IPv4 ranges) and applies a refused consent category to the figures of sleep sessions,
workouts and daily summaries too. It seals health data at rest per user, lets each key carry only
the scopes its service needs, and fixes a consent purge that left record aliases behind (the
unkeyed hash and start time of each purged HealthKit sample). Upgrading is recommended.
