# Open Health Sync v0.1.0

From two sources to thirteen, and from one output format to five. Everything that landed on
`main` since v0.0.2 ships here: eleven new connectors, FHIR R4 and Open mHealth output, CSV and
Parquet exports, outgoing webhooks, background sync with per-source freshness, compression of
the largest table, a personal mode with ready-made recipes, a read-only admin console, a hosted
connection page, erasure of one provider's data when a user disconnects it, a Helm chart for Kubernetes, an
audit log, consent per source and category, a complete user archive, a merged view across sources, and client SDKs for Kotlin, Swift, React Native and Flutter. Still
an early preview: APIs, configuration and schema may change in any 0.x release, so pin the
version you run.

## Install

Container image (`linux/amd64`, `linux/arm64`):

```sh
docker pull ghcr.io/soma-intelligence/open-health-sync:0.1.0
```

The image is tagged `0.1.0` and `edge`. There is no `latest` tag while the version is 0.x.
Binaries for Linux and macOS on amd64 and arm64 are attached below, with `checksums.txt`
(SHA-256). The [quickstart](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/README.md#quickstart)
runs it with Docker Compose, [Render, Fly.io or Railway](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/deploy-platforms.md) host it for you, and the
[Helm chart](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/helm.md) runs it on Kubernetes.

## What's new

- **A merged view across sources.** When a ring and a watch record the same night, or a phone
  and a watch the same steps, reads return the best ranked source's record only, so totals and
  daily summaries count nothing twice. The order is set per user and metric with
  `GET`/`PUT /v1/users/{id}/source-priorities`; every raw record stays stored, and `view=all`
  returns all of them. It applies to the API, daily summaries, FHIR (including `$everything`),
  Open mHealth, exports and the MCP tools.
  [docs/api.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/api.md#several-sources-of-one-metric-the-merged-view)
- **Audit log.** Every authenticated request, every `ohs admin` key command and every
  completed erasure is recorded (who, what, which user, status; never a value or a secret),
  append only and kept after a user's erasure. Read it with `GET /v1/audit`; it is pruned after
  `OHS_AUDIT_RETENTION_DAYS` (default 365). [docs/audit-log.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/audit-log.md)
- **OpenTelemetry traces.** Off by default; set `OTEL_EXPORTER_OTLP_ENDPOINT` to export spans
  over OTLP (HTTP or gRPC) for API requests, pull and processing jobs, webhook deliveries and
  their database queries. Spans never hold a health value or a secret.
  [docs/observability.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/observability.md)
- **Try it without a wearable.** `ohs seed --demo` loads 90 days of synthetic data from six
  overlapping sources and prints a demo API key, so the API, the merged view, FHIR and exports
  can be tried before any provider is connected.
  [docs/demo.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/demo.md)
- **Consent per source and category.** `PUT /v1/users/{id}/consents/{provider}` records which
  categories (activity, heart, sleep, location and more) a user granted, `DELETE` revokes them,
  and every change is kept in a history. Records of a category not granted are never stored,
  revoking deletes what was stored, and `consent.granted` and `consent.revoked` webhooks fire. `OHS_CONSENT_REQUIRED=true` stores nothing from a source until
  consent is recorded. [docs/consent.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/consent.md)
- **Complete user archive.** `GET /v1/users/{id}/archive` streams everything stored for one
  user as one zip (records as NDJSON, a FHIR Bundle, Open mHealth points, every raw payload),
  for data portability requests.
  [docs/exports.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/exports.md#complete-user-archive-data-portability)
- **Eleven new sources.** Oura, WHOOP, Strava, Polar, Fitbit (Google Health API), Suunto,
  Ultrahuman, intervals.icu, Dexcom (CGM glucose) and OMRON (blood pressure) are pulled from
  their cloud APIs with OAuth, with webhooks where the provider has them. Health Connect gets an
  upload endpoint for your Android app, like Apple Health has for iOS. Provider deletions are
  honored: a record deleted upstream is removed and never written again.
- **Health app export import.** `ohs import apple-health export.zip` loads years of Apple
  Health history without an iOS app, in constant memory, and a re-run uploads nothing twice.
- **FHIR R4.** `GET /v1/users/{id}/fhir/Observation` serves samples, blood pressure panels,
  sleep, workouts and daily summaries as FHIR R4 Observations, coded with LOINC and UCUM, with
  the user as a Patient, the Devices the data came from and a Provenance for each Observation.
  `/fhir/Patient/{id}/$everything` returns it all in one Bundle and `/fhir/metadata` a
  CapabilityStatement. The official HL7 validator checks the mapping in CI. [docs/fhir.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/fhir.md)
- **Open mHealth.** `GET /v1/users/{id}/omh/data-points`, every mapping checked against the
  official schemas in the unit tests. [docs/open-mhealth.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/open-mhealth.md)
- **CSV and Parquet exports.** `GET /v1/users/{id}/exports/{dataset}` streams a user's
  samples, sleep, workouts, nutrition or daily summaries as one file, for notebooks and BI
  tools. [docs/exports.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/exports.md)
- **Outgoing webhooks.** `data.written`, `data.deleted`, `user.deleted` and
  `connection.needs_reauth`, signed per Standard Webhooks and retried for about 28 hours.
  Payloads name the user, provider and days, never a health value. Each delivery keeps its
  attempts, can be replayed, and `POST /v1/webhooks/{id}/test` sends a sample of any event type.
  [docs/webhooks.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/webhooks.md)
- **Background sync.** Webhooks first, with backstop pulls that adapt to how often a provider
  notifies, silent subscriptions renewed, and notification pulls served before backfills.
  `GET /v1/users/{id}/freshness` says how up to date each source of a user is, and why not.
- **Personal mode and recipes.** `ohs admin personal setup` readies a one person install and
  prints its env file. `recipes/` holds eight single file Python tools with no dependency (sleep
  report, heart rate and HRV trend, source comparison, weekly digest, HTML dashboard, full
  export, read-only AI token, account connection).
  [docs/recipes](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/recipes/README.md)
- **RR intervals and HRV.** `GET /v1/users/{id}/rr-intervals` serves the stored beat-to-beat
  intervals, and `GET /v1/users/{id}/hrv` the RMSSD, SDNN, pNN50 and mean heart rate of each
  heartbeat series, with MCP tools for both.
  [docs/hrv.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/hrv.md)
- **Menstrual cycles.** `GET /v1/users/{id}/menstrual-cycles` and the `get_menstrual_cycles` MCP
  tool derive cycles from the recorded menstrual flow of Apple Health and Health Connect. They
  restate what was recorded and predict nothing.
  [docs/menstrual-cycles.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/menstrual-cycles.md)
- **Time tags.** `/v1/users/{id}/tags` stores intervals that give context to a user's data
  (illness, injury, travel and more), with `tag.*` webhook events and the `get_tags` MCP tool.
  Context only: nothing is computed from them.
  [docs/time-tags.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/time-tags.md)
- **Admin console.** Set `OHS_CONSOLE=true` and open `/console` with a tenant API key: users,
  connections, freshness and webhook deliveries on one read-only page, failing sources in red.
  [docs/console.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/console.md)
- **Erase a provider's data on disconnect.**
  `DELETE /v1/users/{id}/connections/{provider}?delete_data=true` disconnects and erases every
  record, raw file and job of that user and provider in the background, and
  `DELETE /v1/users/{id}/data/{provider}` does the same for Apple Health or Health Connect. The
  `data.erased` webhook announces the end. A plain disconnect keeps the data, as before.
- **Sync history and connection health.** `GET /v1/users/{id}/sync-runs` shows what each pull
  did and why it failed, `POST /v1/users/{id}/connections/{provider}/sync` pulls now, and every
  connection says whether it is healthy and what to do (reconnect or wait). The
  `connection.broken` and `connection.restored` webhooks tell your backend when that changes.
  [docs/sync-health.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/sync-health.md)
- **Hosted connection page.** `POST /v1/users/{id}/connect-sessions` returns a link to a page
  your instance serves: it lists the providers, shows which ones the user already connected and
  starts the consent, so your backend needs no OAuth screens of its own.
  [docs/connect-page.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/connect-page.md)
- **Backup and restore.** `scripts/backup.sh` writes the database and raw store of a compose
  install to one archive, and `scripts/restore.sh` brings it back; CI runs the full cycle.
  [docs/backup-and-restore.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/backup-and-restore.md)
- **Kubernetes through Helm.** `deploy/helm/ohs` installs every role against a Postgres with
  TimescaleDB you provide, runs the migrations in a pre-install and pre-upgrade Job, keeps the
  generated encryption key across upgrades, and offers Ingress, NetworkPolicy and `helm test`.
  CI installs and upgrades it on kind.
  [docs/helm.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/helm.md)
- **One-click platforms.** `render.yaml`, `railway.json` and `deploy/fly/` deploy the API with
  a TimescaleDB database on Render, Railway or Fly.io, building the image from the repository.
  [docs/deploy-platforms.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/deploy-platforms.md)
- **Client SDKs.** Kotlin (Android and JVM), Swift (iOS and macOS, with a HealthKit sync that
  uploads what changed since the last run), React Native and Flutter, each covering every API
  route, with example apps for iOS, Android and React Native. AGPL-3.0 like the server; install
  them from the repository, they are not on package registries yet.
  [docs/sdks](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/sdks/README.md)
- **Fair pulls under rate limits.** Webhook and manual pulls go first and backfills last, at most
  `OHS_PULLS_PER_PROVIDER` (default 4) pulls of one provider run at once, and a 429 pauses the
  whole provider with a growing backoff.
  [Provider rate limits](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/background-sync.md#provider-rate-limits)
- **Recorded replay tests.** `make record PROVIDER=<slug>` records a real account's answers,
  anonymized on the contributor's machine, and CI replays every committed recording through its
  connector. The first is a three day Apple Watch export covering 23 data types.
  [docs/connectors/recording.md](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/connectors/recording.md)
- **Roadmap.** Health records (EHR) through SMART on FHIR are planned.
- **Smaller and faster storage.** `quantity_samples` chunks older than 30 days are compressed
  (about 7 times less disk in our benchmark of 10.5 million samples), and a history import into
  a compressed period is about 34 times faster.
- **No doubled nights or workouts.** When the watch and the phone (or a sleep app) both record
  the same night or workout through Apple Health, the merged view now returns it once, keeping
  the watch's session.
- **Apple Health speeds are kept.** Walking and running speed in `km/hr` or `mi/hr` were parked
  as unit errors and are now stored in `m/s`. An instance upgraded to 0.1.0 replays the parked
  records.
- **Fuzzed uploads.** The Apple Health upload parser is fuzzed in CI, which checks that no
  parse error quotes the uploaded health data. Thank you to @yashthakur2008, our first outside
  contributor (#87).

The full list is in the [changelog](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/CHANGELOG.md#010---2026-10-13).

## Upgrade notes

Take a backup first, then set `OHS_VERSION=0.1.0` in your `.env`, pull and recreate (the
[self-hosting guide](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/self-hosting.md#upgrading)
has the full steps). A v0.0.2 configuration starts as is, with three changes in behavior:

- **Docker Compose now publishes the API on `127.0.0.1` only.** A v0.0.2 install reached from
  another machine on port 8080 stops answering there: put a reverse proxy with TLS in front
  (the guide has an example) or set `OHS_HTTP_BIND=0.0.0.0` in `.env` to publish plain http on
  every interface as before.
- **`/metrics` is closed by default, so an existing Prometheus scrape gets 403.** Set
  `OHS_METRICS_TOKEN` (16 characters or more, `openssl rand -hex 32`) and give it to Prometheus
  as a bearer token (`authorization: { credentials: ... }`), or set `OHS_METRICS_LISTEN` (for
  example `127.0.0.1:9464`) to serve it on a private address of its own. See
  [Metrics](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/self-hosting.md#metrics).
- **Reads return the merged view by default.** A user with several sources of one metric now
  gets one record where two sources overlap, from the best ranked source: samples, sleep,
  workouts, FHIR, Open mHealth, exports and MCP. `GET .../daily` returns one summary per day
  instead of one per provider and day. A client that needs every source's rows, as in v0.0.2,
  passes `view=all`. See [the merged view](https://github.com/soma-intelligence/open-health-sync/blob/v0.1.0/docs/api.md#several-sources-of-one-metric-the-merged-view).

Migrations `0008` to `0034` apply on start (CI upgrades a v0.0.2 database to this release and
checks that its data is still served). Two of them touch large tables:

- **`0015`** drops the unique index `quantity_samples_dedup_key` (duplicates are now found by
  the writer) and, on a TimescaleDB build with the Timescale License, turns on compression of
  `quantity_samples` chunks older than 30 days. The first compression runs in the background
  after the upgrade. An Apache-only TimescaleDB build keeps the table uncompressed and works
  the same.
- **`0014`** adds two partial indexes on `quantity_samples` and `category_samples`. On a large
  database the first start takes longer while they build.

Each new connector stays off until its keys are set (`OHS_<PROVIDER>_CLIENT_ID` and
`OHS_<PROVIDER>_CLIENT_SECRET`; see `.env.example` and the guide of each connector).
`ohs doctor` lists which are on. Webhook endpoints must be public `https` URLs unless you set
`OHS_WEBHOOK_ALLOW_PRIVATE=true`.

## Known limitations

- Fitbit needs a Google Health API project, and Google is not onboarding new ones yet. Most
  other cloud sources need a developer or partner app of your own with the provider; each
  connector guide says which.
- FHIR R4 has no bulk export (`$export`) yet.
- ECG recordings are stored but not served yet.
- After a hard kill, a job that was in flight is picked up again only after its 10 minute
  visibility timeout. One database and one raw store per instance.
